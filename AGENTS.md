# Jandi Real2Sim Agent Guide

## Project role

This repository identifies and validates a realistic actuator model for the Jandi robot's DYNAMIXEL MX-106 operated in Position Control Mode 3.

The main pipeline is:

physical experiment
→ parameter identification
→ MuJoCo single-joint validation
→ reusable actuator model

Full robot reinforcement-learning policy training belongs to a separate repository.

## Working rules

- If the user asks only for analysis or explanation, do not modify files.
- Do not invent numerical values.
- Inspect the current repository files and actual result files before making claims about parameters or experiment results.
- Preserve existing user changes and unrelated work.
- Avoid unrelated refactoring during targeted fixes.

If documentation disagrees with current code, config, result YAML, or experiment metadata, prefer the current executable/config/result state and report the discrepancy.

## Source of truth

For numerical or experimental claims, inspect the relevant sources in roughly this order:

1. current experiment/config YAML
2. selected/fitted result YAML
3. experiment metadata
4. validation summaries
5. current source code
6. README documentation

Do not treat old example values in documentation as current fitted parameters.

## Raw-data safety

`data/raw/` contains experimental evidence and must be treated as immutable unless the user explicitly requests otherwise.

- Never overwrite an existing raw attempt.
- New runs must use the existing attempt/timestamp scheme.
- Do not delete failed attempts merely because they are invalid.
- Do not silently change raw telemetry to match a model.

Calibration reports may be read and analyzed, but hardware calibration must not be rerun automatically.

## Hardware safety

Never autonomously execute commands that can move or torque-enable a physical DYNAMIXEL.

This includes:

- hardware experiment trajectories
- sign-test motion
- drop tests
- torque-enable sequences
- calibration motion
- full campaign acquisition

When such execution is required, provide the exact command and let the user run it unless the user explicitly instructs otherwise.

Do not weaken position, current, PWM, voltage, temperature, or mechanical safety limits merely to make an experiment complete successfully.

## Long-running work

Do not autonomously start:

- complete fitting pipelines
- broad MuJoCo sweeps
- long validation batches
- hardware campaigns

unless explicitly requested.

Short deterministic checks may be run after code changes.

## Model semantics

Keep the following quantities conceptually separate:

- measured DYNAMIXEL Present Current
- model-predicted current
- electromagnetic motor torque
- friction torque
- final actuator/output torque

The current generated by the DC motor model is a predicted diagnostic/model quantity. It is not automatically equivalent to the measured Present Current waveform.

The identified backlash parameter is an `effective-state backlash` / effective dead-zone quantity. Do not describe it as pure physical gear-tooth backlash unless supported by separate evidence.

Keep M3 nominal and M3 + effective-backlash variants distinct.

## Units and signs

Use SI units internally unless an interface explicitly requires raw DYNAMIXEL units.

Preserve the repository's established definitions for:

- joint positive direction
- encoder direction
- PWM direction
- current direction
- gravity torque sign
- upright q=0

Do not “fix” a sign convention solely because another robotics package uses a different convention.

## Results policy

`results/` is intentionally local-only and is not tracked by Git.

Canonical experiment outputs may include:

- fitted parameter YAML files
- selected model YAML
- compact validation summaries
- human-readable reports
- aggregate metrics

These files remain under the local `results/` directory.

For persistent project context, summarize the currently adopted model,
parameters, validation conclusions, and important result paths in
`CURRENT_STATE.md`.

Do not copy large generated plots or per-sample traces into the repository
solely to provide context to an agent.

## Verification

After Python changes, run the relevant focused tests.

For changes that can affect multiple components, run:

`uv run python -m unittest discover -s tests`

Do not claim that tests pass unless the command actually completed successfully.

Do not change or remove a test solely because a new implementation fails it; first determine whether the implementation or the test contract is wrong.

## Scope discipline

Prefer the smallest change that preserves the current experimental contract.

When investigating a problem:

1. inspect the directly relevant code/config/result,
2. reproduce or explain the issue,
3. identify the cause,
4. propose a change,
5. modify only when requested,
6. verify with focused tests.
